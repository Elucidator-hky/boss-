# 架构与原理

```text
Codex / Claude Code 会话 A、B
  ↕ 各自 stdio MCP
mcp-server/server.js（每会话一个适配器）
  ↕ WebSocket /mcp
mcp-server/bridge-runtime.js（每端口一个共享桥接）
  ↕ WebSocket /，默认 127.0.0.1:8765
Chrome 扩展 src/background/sw.js
  ↕ chrome.tabs.sendMessage
src/content/bridge.js（读 DOM、派发事件）
src/content/inject.js（读取页面请求返回的岗位信息）
```

## 连接与控制权

适配器先验证共享桥接协议和版本，再向 AI 发布工具。旧服务占端口或协议不匹配时启动失败；扩展是否在线通过 `connection_status` 另行核对。

一个会话首次操作页面后持有控制权，直到它调用 `release_control` 或断开。其他会话仍可自检，但页面操作会明确报忙。控制权是完整工作流的锁，保证两个 AI 任务不能交错切换、填入和发送；用户本人手动操作仍须协商，工具每次外发前要重新核对目标。

桥接串行转发命令，并统一限制 `send_reply`、`chat_action`、`greet`、`dom_click` 的间隔为 8–15 秒。超时只报告错误，不重发；已触发操作是否成功必须回读页面确认。

## 页面与账号限制

扩展操作使用合成 DOM 事件，不连接 CDP；这不能保证平台无法识别自动化。账号风控的实际原因需以警告和操作日志核查，不能从一个工具名称推出。出现异常或验证码即停止自动操作，由本人处理。

页面改版可能使选择器、岗位缓存和发送逻辑失效。先用 `debug_dom` 检查实际结构；需要点击时仍走本 MCP 的 `dom_click`。发送默认优先点击可见 `.btn-send`，否则派发 Enter；结果 `attempted` 和 `verified: false` 表示仍需回读，不是送达证明。

## 可选新消息监听

扩展观察顶部未读数和当前对话 HR 消息数量；触发后由桥接追加到信号文件。`watch-messages.sh` 使用持久游标，检测新行后打印并退出；600 秒没有信号也退出一次供宿主检查。重挂可接着消费间隔内的消息。

该脚本需要 zsh（macOS/Linux），使用：

```sh
zsh watch-messages.sh
```

`BOSS_SIGNAL_FILE` 要与 `connection_status.signalFile` 一致；`BOSS_CURSOR_FILE` 可自定义游标文件，默认信号文件加 `.cursor`；`BOSS_WATCH_TIMEOUT` 默认 600 秒。同一份游标只运行一个监听器。

**脚本本身不会唤醒 AI。** 只有宿主支持“后台命令完成通知回到当前 AI 会话”时，才可把它注册为后台任务；处理后重新注册。普通终端的 `&` 只会输出文字，不会自动续聊。宿主不支持时，由用户手动要求检查消息；Windows 可直接用 MCP 读消息，不依赖 zsh。
