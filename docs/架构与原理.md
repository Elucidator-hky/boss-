# 架构与原理

## 整体架构

```
   AI（Claude Code / Codex）           大脑：读 JD、判断岗位、组织措辞
        ↕  MCP over stdio
   mcp-server/server.js                中转：MCP 工具 ↔ WebSocket
        ↕  WebSocket 127.0.0.1:8765
   src/background/sw.js                扩展后台：转发命令给当前 Boss 标签
        ↕  chrome.tabs.sendMessage
   src/content/bridge.js               在页面里执行：读消息 / 点击 / 填写 / 发送
   src/content/inject.js               MAIN world：拦截 Boss XHR 拿结构化职位数据
        ↕  DOM
   Boss 直聘网页
```

## 为什么这样最安全（反检测）

Boss 有四层反自动化：webdriver 指纹、CDP 检测、Canvas 熵、URL 签名——Playwright/Selenium 一上就被屏蔽。

本方案**不用任何自动化框架**：扩展是普通 Chrome 扩展，跑在你**平时登录的真实浏览器**里，用你的真实会话和指纹，所有操作都是**在页面内派发真实的鼠标/键盘事件**。从 Boss 视角看，跟真人操作没有区别。

## 数据流

**读**（零风险）：`read_conversations` / `read_current_page` / `read_jobs` 等 → bridge.js 读 DOM 或 inject.js 拦截的 API 缓存 → 原路返回。

**写**（真实对外，谨慎）：`send_reply` / `chat_action` / `greet` → bridge.js 派发真实事件链（pointerdown→mousedown→pointerup→mouseup→click，输入框用 contenteditable + input 事件）→ Boss 处理。server.js 对写操作**强制拟人间隔**（8-15s 随机），防机器般连续操作触发风控。

## 实时消息唤醒机制（盯梢）

让「HR 发消息」变成「唤醒 AI」，靠一条接力：

1. **扩展检测**（bridge.js）：MutationObserver 盯页面，读顶部导航「消息」未读计数 `.nav-chat-num`——**只在数字增大（真有新消息）时**才发信号。这个元素在所有页面都有（含搜索页），且自己发消息/已读不会让它变大 → 天然过滤误报。
2. **写信号**（sw.js → server.js）：扩展把事件经 WebSocket 发给 server，server 往信号文件追加一行。
3. **盯梢**（watch-messages.sh）：每秒比对信号文件行数，一变就打印内容并 `exit`。
4. **唤醒**：盯梢进程退出 → 触发 agent 的后台任务通知 → AI 醒来 `read_conversations` 处理。

> ⚠️ 盯梢是**一次性**的（触发即退出），AI 处理完要**再挂一个**继续盯。可另配一个低频定时任务当「看门狗」：发现盯梢进程没了就补挂，双保险。

## 关键技术点（踩坑沉淀）

- **切换对话要清职位缓存**：inject.js 拦截的职位数据是异步推来的，`open_conversation` 后必须清空旧缓存、等新数据，否则 `read_current_page` 会返回上一个对话的残留 JD。
- **左侧对话点击**：监听在内层 `.friend-content`（带埋点属性），事件要派发到它，不是 li。
- **发送消息**：对输入框（`#chat-input`，contenteditable）模拟 Enter keydown/keyup，无需找发送按钮。
- **发送后必回读**：工具返回成功 ≠ 真实送达，必须 `read_current_page` 看聊天记录里出现自己那条才算数。
- **工具栏动作有门控**：发简历/换微信/换电话在双方互发过消息前点击被静默忽略。
- **消息列表是虚拟滚动**：读消息前先把容器滚到底，保证最新消息已渲染。
